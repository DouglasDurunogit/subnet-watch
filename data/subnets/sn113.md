# Elo subnet

Bittensor subnet 113. Its one job is to make the Elo browser faster for the AI agents that
drive it.

The browser is built by the project and is closed source. The part an agent talks to, the
**agent layer**, is open (`package/elo-browser` in https://github.com/elobrowser/browser, MIT),
and the browser can run any single command with another build of it
(`elo-browser nodejs --sdk-path <bundle>`). That is what the competition is about:

| Who | Does what |
| --- | --- |
| Miner | Improves the agent layer and publishes the result |
| Validator | Runs every submission and the baseline on the same tasks, on one machine, with one reference agent |
| Baseline | The agent layer at the commit pinned in `scripts/build-baseline.sh` |

A submission has to finish the tasks first; among those that do, the fastest leads and takes
the miner reward until something clearly faster arrives.

- Rules, scoring and rewards: [`docs/competition.md`](docs/competition.md)
- Taking part as a miner: [`docs/mining.md`](docs/mining.md)
- Running a validator: [`docs/validating.md`](docs/validating.md)
- Every measured submission and the current leader: https://github.com/elobrowser/submissions

## Install and check

```bash
sudo apt-get install -y bubblewrap
npm ci
npx playwright-core install chromium
scripts/build-baseline.sh
npm run check
```

To compare built bundles with the baseline without any chain:

```bash
node src/cli/validator.ts --local-entries entries.json --per-family 2
```

`entries.json` is a list of `{ "uid", "commitBlock", "fingerprint", "sdkPath" }`. `miner.ts pack`
prints the fingerprint and `miner.ts check` the `sdkPath`. The leader is remembered in a state
file under `.work/` and measured again on every run.

## Where things are

| Path | Contents |
| --- | --- |
| `src/tasks` | Twelve families of self-hosted task sites, sixty tasks a round. Pass or fail comes from server state only. A standing test runs each family's scripted solution on several seeds |
| `src/runner` | One run: a fresh task space, the reference agent (model-driven or scripted), timing |
| `src/sandbox` | On Linux, the box every run and every build happens in: no network except the run's task site (which answers the browser only), none of the machine's files, nothing kept. A test tries from inside what a hostile entry would try |
| `src/submission` | Deterministic archive, strict unpacking, the pre-measurement check, the validator-side build |
| `src/scoring` | Qualifying, standard time, speed-up, the rule for taking the lead, weights |
| `src/validator` | Intake of published submissions and the two-stage round |
| `src/cli` | `miner.ts` and `validator.ts` |
| `src/standin` | A stand-in for the browser, for development (below) |
| `chain/` | Python bridge to Bittensor (SDK 11): subnet facts, published lines, publishing, weights |

## The stand-in browser

`src/standin` offers the browser's bindings (`globalThis.elo`) on top of a plain headless
Chromium, so the whole pipeline can be developed and tested on Linux without the browser. **Stand-in timings
say nothing about the real browser** and are never used for rewards.

`--browser real` runs the same pipeline with the real browser: inside the sandbox with
`--elo-app` (Linux), or against an installed one. An installed browser keeps one profile, so
the validator clears the task site's data and the HTTP cache before each run and refuses to
measure if its probe still finds data crossing between runs (`docs/validating.md`).
